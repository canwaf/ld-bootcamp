What you’ll learn

By the end of this module you’ll be able to:

  • look up a term and find its label, its definition and the vocabulary that defines it
  • read a term’s documentation page and its triples, and match each field to its predicate
  • follow a class up its hierarchy to everything its instances also are
  • say whether a term is a class, a property or a SKOS concept
  • predict the types your data acquires from the properties it uses
  • tell a rule about a property apart from a hint

You’ll need a web browser, a terminal with curl, and the rdfpipe command that comes with the rdflib package from Module 4.

SKOS, SOSA and Dublin Core are quoted from the files their publishers serve today. The Defra terms are quoted from version 0.1.0 of Defra’s domain model, which its authors describe as a work in progress, so details may change. URIs starting ex: are made up for this module.

A term is a URI

In Module 3 you met the vocabularies that answer each kind of question: SKOS for concepts, SOSA for observations, Dublin Core for publishing, and Defra’s own terms for regulation and water. Every predicate and class in them is a URI. So, like the sampling point in Module 1, a term can be looked up, and looking it up should tell you what it means.

That is how you read a vocabulary: one term at a time, by following its URI.

SOSA: a term served as Turtle

Ask for the class sosa:FeatureOfInterest in Turtle. -L tells curl to follow redirects, which most vocabulary URIs use:

curl -L -H "Accept: text/turtle" http://www.w3.org/ns/sosa/FeatureOfInterest

What comes back is the whole SOSA vocabulary, a few hundred triples. The W3C serves the same file at every SOSA term’s URI, and you find the term you asked for inside it:

sosa:FeatureOfInterest a rdfs:Class ; a owl:Class ;
  rdfs:label "Feature Of Interest"@en ;
  skos:definition "The thing whose property is being estimated or calculated in the course of an Observation to arrive at a Result or whose property is being manipulated by an Actuator, or which is being sampled or transformed in an act of Sampling."@en ;
  rdfs:comment "The thing whose property is being estimated or calculated in the course of an Observation to arrive at a Result or whose property is being manipulated by an Actuator, or which is being sampled or transformed in an act of Sampling."@en ;
  skos:example "When measuring the height of a tree, the height is the observed ObservableProperty, 20m may be the Result of the Observation, and the tree is the FeatureOfInterest. A window is a FeatureOfInterest for an automatic window control Actuator."@en ;
  rdfs:isDefinedBy sosa: .

This is ordinary Turtle, written by the W3C. The vocabulary describes itself with triples, using the same predicates you’ve used to describe sampling points.

Dublin Core: a term behind several redirects

curl -L -H "Accept: text/turtle" http://purl.org/dc/terms/title

This one passes through several redirects before it reaches the Dublin Core terms file. Inside it:

dcterms:title
    dcterms:issued "2008-01-14"^^<http://www.w3.org/2001/XMLSchema#date> ;
    a rdf:Property ;
    rdfs:comment "A name given to the resource."@en ;
    rdfs:isDefinedBy <http://purl.org/dc/terms/> ;
    rdfs:label "Title"@en ;
    rdfs:range rdfs:Literal ;
    rdfs:subPropertyOf <http://purl.org/dc/elements/1.1/title> .

The file writes the prefix as dcterms:, where this course writes dct:. Both stand for http://purl.org/dc/terms/, so they name the same terms. As Module 2 said, a prefix is only shorthand, and the full URI is what counts.

SKOS: a hash URI, served as RDF/XML

SKOS terms are hash URIs, such as http://www.w3.org/2004/02/skos/core#Concept. A client never sends the part after the # to the server. It asks for the document and looks for the part itself, exactly as with AN-CORBY#Geometry in Module 2. So any SKOS term gets you the whole SKOS document.

curl -i -L -H "Accept: text/turtle" "http://www.w3.org/2004/02/skos/core#Concept"

Read the last content-type header: it says application/rdf+xml. You asked for Turtle, and SKOS is only published as RDF/XML, so that’s what came back. Module 4 showed how to deal with that: rdfpipe converts it, and it reads straight from a URL. -i xml says the input is RDF/XML, as the header told you:

rdfpipe -i xml -o turtle http://www.w3.org/2004/02/skos/core > skos.ttl

Open skos.ttl and search for the block that starts with skos:Concept. Turtle keeps everything said about one subject together, from the subject to the full stop, so that block is the whole of what SKOS says about the term:

skos:Concept a owl:Class ;
    rdfs:label "Concept"@en ;
    rdfs:isDefinedBy <http://www.w3.org/2004/02/skos/core> ;
    skos:definition "An idea or notion; a unit of thought."@en .

What a term says about itself

The three terms were published by different organisations in two formats, and they all answer the same handful of questions. These are the predicates to look for:

rdfs:label
The term’s name, for people: Feature Of Interest.
rdfs:comment or skos:definition
What it means. This is the part to read before you use a term. SOSA gives both; SKOS gives a definition; Dublin Core gives a comment.
rdfs:isDefinedBy
The vocabulary the term belongs to, as a URI you can follow to read the rest of it.
a
What kind of term it is: a class, or one of the kinds of property. Classes, properties and concepts covers how to tell.
rdfs:subClassOf or rdfs:subPropertyOf
Where it sits in a hierarchy: the more general class or property it narrows.
rdfs:domain and rdfs:range
For a property, what its subjects and objects are. Domain and range draw conclusions covers what these do to your data.

The page and the triples

Most vocabularies are published twice: as triples, for programs, and as a documentation page, for people. The Dublin Core terms are listed on the DCMI Metadata Terms page, SOSA’s terms in the Semantic Sensor Network Ontology specification, and SKOS’s in the SKOS namespace document. Each entry on these pages is a term’s triples laid out as a form, with a field for each predicate.

Here is the entry for title on the DCMI page, set against the triples you fetched:

The DCMI page’s entry for title, field by field

LabelTitlerdfs:label
DefinitionA name given to the resource.rdfs:comment
Has Rangerdfs:Literalrdfs:range
Subproperty ofTitle, in the older /elements/1.1/ namespacerdfs:subPropertyOf

The fields are the predicates, renamed for people. The page and the triples say the same things, so once you know which field is which predicate you can read either one.

When one word changes the predicate

The same page’s entry for publisher has a field called Range Includes, where title has Has Range. The different wording is a different predicate: Has Range is rdfs:range, and Range Includes is dcam:rangeIncludes. SOSA’s entry for sosa:hasFeatureOfInterest does the same, with Domain Includes and Range Includes for schema:domainIncludes and schema:rangeIncludes. Hints that draw no conclusions explains why that one word matters for your data.

When the page sends you elsewhere

The SKOS namespace document gives the definition of skos:Concept as a link to section 3 of the SKOS Reference, a separate document. The triples carry the definition itself: An idea or notion; a unit of thought. The page also lists skos:notation simply as a property, where the triples type it as an owl:DatatypeProperty. When a page and its triples differ in detail, read the triples: they are what your data’s meaning rests on.

When there is no page

Defra’s domain model has no documentation page yet. Its definitions exist only as Turtle files. Once you can match fields to predicates, that is no obstacle, because Turtle already lays a term out like an entry: the term’s URI first, then one predicate and its value on each line, until the full stop. Reading a vocabulary file reads the Defra terms that way.

Reading a vocabulary file

Defra’s domain model defines its terms under environment.data.gov.uk, in three namespaces:

defra-core:
http://environment.data.gov.uk/ontology/core/
defra-reg:
http://environment.data.gov.uk/ontology/regulation/
defra-water:
http://environment.data.gov.uk/ontology/water/

Follow one of these terms today and you get 404 Not Found: the terms have been minted, but nothing answers at their addresses yet. For now, the definitions are in three Turtle files on GitHub. Download them:

curl -O https://raw.githubusercontent.com/agrimetrics/defra-ontology/main/defra-core-ontology.ttl
curl -O https://raw.githubusercontent.com/agrimetrics/defra-ontology/main/defra-regulation.ttl
curl -O https://raw.githubusercontent.com/agrimetrics/defra-ontology/main/defra-water.ttl

The URI and the file are separate things. The URI is the term’s identity, and it stays the same whether or not it can be looked up yet. The file is just where you can read the definition for now. Your data uses the URI.

The ontology describes itself

A vocabulary defined with OWL is usually called an ontology. Each file starts with a description of the ontology as a whole. Here is the start of defra-water.ttl:

<http://environment.data.gov.uk/ontology/water>
    a owl:Ontology ;
    dcterms:title "DEFRA Water Ontology"@en ;
    dcterms:description "Water reusable classes and properties for DEFRA Linked Data APIs, covering WaterBody, Catchment, DischargePoint, EffluentType, WaterDischargeActivity."@en ;
    dcterms:creator "Department for Environment, Food and Rural Affairs"@en ;
    dcterms:publisher "Department for Environment, Food and Rural Affairs"@en ;
    dcterms:license <http://www.nationalarchives.gov.uk/doc/open-government-licence/version/3/> ;
    dcterms:created "2026-07-01"^^xsd:date ;
    owl:versionInfo "0.1.0" ;
    rdfs:seeAlso <http://environment.data.gov.uk/catalog> .

These are the Dublin Core predicates from Module 3, now describing a vocabulary in place of a dataset: its title, who published it, its licence and its version.

A term, in the file

Further down is the class you’ll use in Module 6 for a discharge permit:

defra-water:WaterDischargePermit
    a owl:Class ;
    rdfs:label "Water Discharge Permit"@en ;
    rdfs:comment "A permit authorising the discharge of effluent to controlled waters, subject to conditions."@en ;
    rdfs:subClassOf defra-reg:Permit .

It has a label, a definition, a type and a superclass. Read it as you read the DCMI page: the subject is the term, and each line is a field. Defra publishes no page for this term, so this block is its documentation. To find any Defra term, open the file in a text editor or on GitHub and search for its local name, such as WaterDischargePermit.

When a term doesn’t say everything

Compare it with the SKOS, SOSA and Dublin Core terms and three things are missing or out of step. Each one is worth knowing how to handle, because you’ll meet them in other vocabularies too.

  • No rdfs:isDefinedBy. No Defra term says which ontology defines it. The URIs still tell you: a term starting http://environment.data.gov.uk/ontology/water/ belongs to the ontology http://environment.data.gov.uk/ontology/water, the one whose header you just read.
  • A description that disagrees with the triples. The water ontology’s description lists DischargePoint among the things it covers. In fact DischargePoint is defined in the regulation ontology, so its URI is defra-reg:DischargePoint, and the water file defines no EffluentType or WaterDischargeActivity yet. When a description and the definitions disagree, go by the definitions: they are what your data will use.
  • Terms with no definition. defra-core:Site has a label and a superclass but no comment, and defra-reg:Driver has the comment “To be defined.” When the definition is missing, read what is there: the superclass, and the properties that point at the term. They tell you a lot, as the rest of this module shows.

Climbing the class hierarchy

rdfs:subClassOf says that every instance of one class is also an instance of another. Every water discharge permit is a permit. Follow the superclasses up from a class, one file at a time, and you reach everything its instances are:

Each step is in a different place. WaterDischargePermit is defined in the water ontology, Permit in the regulation ontology, and dcat:Resource in DCAT. The discharge point climbs from regulation to core to GeoSPARQL. So a discharge point is a site and a geo:Feature, the same class as AN-CORBY in Module 3, which is why a discharge point can have a location on a map.

Conclusions go up the hierarchy and never down. Every water discharge permit is a permit, but a permit isn’t necessarily a water discharge permit. If your data should say the narrower class, it has to state it.

A class can have several superclasses, just as a thing can have several types. That’s five classes from three other vocabularies, so any program that understands FOAF, PROV or the W3C Organization ontology already knows something about a Defra permit holder. And those vocabularies have hierarchies of their own if you keep following.

Classes, properties and concepts

Every term you look up is one of three kinds of thing, and the kind decides where it goes in a triple.

How to tell what kind of term you’re reading
KindIts type saysWhere it goesExamples
Classowl:Class or rdfs:ClassThe object of adefra-reg:Permit, sosa:FeatureOfInterest
Object propertyowl:ObjectPropertyThe predicate, with a link as its objectdefra-reg:permitSite, sosa:hasSample
Datatype propertyowl:DatatypePropertyThe predicate, with a literal as its objectdefra-core:identifierValue, skos:notation
Other propertyrdf:Property or owl:AnnotationPropertyThe predicatedct:title, skos:prefLabel
Conceptskos:ConceptThe object of a property whose range is skos:Conceptsampling-point-type:SA, determinand:0111

There’s a naming habit that helps: class names start with a capital letter (Permit) and property names with a small one (permitSite). It’s a habit, not a rule, so check the type when it matters.

Schema and controlled values

Classes and properties are the schema: the kinds of thing there are and the ways they can be related. An ontology defines them, and it rarely changes.

Concepts are controlled values: the determinands, the sampling point types, the kinds of permit. They aren’t defined in an ontology at all. Each one is an instance of skos:Concept, published in a concept scheme that is listed in a catalogue as a dataset, as in Module 3. A new kind of sampling point is a new row of data in its scheme, and nobody has to edit an ontology.

The two meet in properties like defra-core:hasClassification. The ontology says its object is a concept. Which concepts exist is up to the scheme.

Domain and range draw conclusions

Module 3 said a property’s range says what its object should be. In RDFS it’s stronger than that. The domain and range of a property are rules for drawing conclusions:

  • if a property has a domain, the subject of any triple that uses it is an instance of that class
  • if a property has a range, the object of any triple that uses it is an instance of that class

Here is the property that links a discharge point to the sampling point that monitors it:

defra-water:monitoredAt
    a owl:ObjectProperty ;
    rdfs:subPropertyOf dcterms:relation ;
    rdfs:label "monitored at"@en ;
    rdfs:comment "Relates a discharge point to the sampling point at which its discharges are monitored. Via a permit's discharge points, this says how the permit is monitored."@en ;
    rdfs:domain defra-reg:DischargePoint ;
    rdfs:range sosa:FeatureOfInterest .

Now take one triple that uses it. Nothing else is said about ex:discharge-point:

ex:discharge-point defra-water:monitoredAt <https://environment.data.gov.uk/water-quality/sampling-point/AN-CORBY> .

That one triple makes all of these true:

What one monitoredAt triple makes true
SubjectPredicateObjectBecause
ex:discharge-pointadefra-reg:DischargePointthe domain
ex:discharge-pointadefra-core:Sitethe hierarchy
ex:discharge-pointageo:Featurethe hierarchy
<sampling-point/AN-CORBY>asosa:FeatureOfInterestthe range
ex:discharge-pointdct:relation<sampling-point/AN-CORBY>the superproperty

The last row comes from rdfs:subPropertyOf, which works for properties the way rdfs:subClassOf works for classes: anything related by monitoredAt is also related by the broader dct:relation, so a program that only knows Dublin Core can still see the two are related.

The range agrees with the Environment Agency, which already types AN-CORBY as a sosa:FeatureOfInterest. That’s the vocabulary working as intended: whatever the discharge point is monitored at is something that is observed.

Whatever the author meant

These conclusions follow from the triple, not from what its author had in mind. Suppose someone writes the link straight from a permit to the sampling point, skipping the discharge point:

ex:permit defra-water:monitoredAt <https://environment.data.gov.uk/water-quality/sampling-point/AN-CORBY> .

The domain now makes the permit a discharge point, and so a site and a geo:Feature, as well as a permit: a permit with a place on a map. Nothing rejects the triple or warns about it. RDFS only ever adds conclusions; it doesn’t check data. Checking data against the shape you meant is a job for SHACL, in a later module.

That’s why reading a property’s domain and range comes before using it. They tell you what your data will say, whether you meant it to or not.

A range with no domain

defra-core:hasClassification has a range and no domain:

defra-core:hasClassification a owl:ObjectProperty ;
    rdfs:label "has classification"@en ;
    rdfs:comment "Relates a resource to its classification, a resource can have multiple classifications."@en ;
    rdfs:range skos:Concept ;
     .

With no domain, the property says nothing about its subject, so anything can be classified: a sampling point, a water body or a permit. The range makes every classification a skos:Concept. That conclusion is the one the property exists for: it guarantees a classification is a concept, with a notation, a label and a scheme, and never a typed-in string. It’s the fix for River, river and Rivers from Module 1, written as a rule.

A domain that is one of two classes

A condition on a permit puts a bound on something, and so does a limit. The property that names what is bounded has a domain written as a blank node:

defra-reg:regulatedProperty a owl:ObjectProperty ;
    rdfs:label "regulated property"@en ;
    rdfs:comment "The observable property (substance, parameter) that this condition or limit places a bound on."@en ;
    rdfs:domain [ a owl:Class ; owl:unionOf (defra-reg:Condition defra-reg:Limit) ] ;
    rdfs:range sosa:ObservableProperty ;
     .

The blank node is a class with no name of its own: the union of Condition and Limit, meaning everything that is one or the other. ( ) is Turtle for a list.

ex:condition defra-reg:regulatedProperty determinand:0111 .

From this triple, ex:condition is a condition or a limit, but nothing says which. Neither a defra-reg:Condition nor a defra-reg:Limit follows. To know which, you need another triple, such as a permit’s defra-reg:hasCondition, whose range is defra-reg:Condition.

The range makes the determinand a sosa:ObservableProperty. It’s already a skos:Concept, and it can be both: a code in a scheme, and a property of water that can be observed.

Hints that draw no conclusions

Not every vocabulary uses rdfs:domain and rdfs:range. Look up sosa:hasFeatureOfInterest, the property linking a sampling or an observation to what it studies:

sosa:hasFeatureOfInterest a owl:ObjectProperty ;
  rdfs:label "has feature of interest"@en ;
  …
  schema:domainIncludes sosa:Observation ;
  schema:domainIncludes sosa:Actuation ;
  schema:domainIncludes sosa:Sampling ;
  schema:rangeIncludes sosa:FeatureOfInterest ;
  schema:rangeIncludes sosa:Sample ;
  owl:inverseOf sosa:isFeatureOfInterestOf ;

schema:domainIncludes and schema:rangeIncludes come from schema.org. They say what the subject and object are expected to be, and they draw no conclusions. SOSA declares them as owl:AnnotationProperty, which is OWL’s way of saying “for people to read, not for drawing conclusions”. Use sosa:hasFeatureOfInterest on anything you like and it stays what it was.

Hints suit a vocabulary meant for many kinds of observation in many fields. A strict domain on sosa:hasFeatureOfInterest would give a type to every subject that used it, whether the type fitted or not.

Dublin Core does the same with its own hint, dcam:rangeIncludes. On dct:publisher:

dcterms:publisher
    dcam:rangeIncludes dcterms:Agent ;
    …
    rdfs:comment "An entity responsible for making the resource available."@en ;

A publisher is expected to be an agent, but saying dct:publisher doesn’t make it one. Compare dct:title, earlier in this module, which has a real rdfs:range of rdfs:Literal.

So when you read a property, the first question is which kind of statement you’re looking at:

  • rdfs:domain and rdfs:range are rules, and your data gains types from them
  • schema:domainIncludes, schema:rangeIncludes and dcam:rangeIncludes are hints for the people writing the data

Summary

In this module you learned that:

  • a term is a URI, and reading a vocabulary starts by following it, or by reading the file that defines it when it can’t be followed yet
  • a term describes itself with triples: a label, a definition, the vocabulary that defines it, its type, and where it sits in a hierarchy
  • a documentation page shows a term’s triples as labelled fields, and a Turtle block can be read the same way when there is no page
  • rdfs:subClassOf carries an instance up to every superclass, and conclusions never go down to a narrower class
  • classes and properties are a vocabulary’s schema, and SKOS concepts are controlled values published as data in a scheme
  • rdfs:domain and rdfs:range are rules: using a property gives its subject and object their types, whatever the author meant
  • a union domain says a subject is one of several classes without saying which
  • schema:domainIncludes, schema:rangeIncludes and dcam:rangeIncludes are hints, and draw no conclusions

Module 6 uses these terms to describe one real thing: a water discharge permit, its discharge point and its holder, linked to AN-CORBY.
